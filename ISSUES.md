## 2. Offsets / shifts mode - remaining limitations

Offset mode is enabled by default in the demo (`main.ts` passes `shifts: true`). The layout was
reworked: shifts are normalized to the pattern period (the cut region is the repeat unit), the
margin ring adjacent to the visible area renders unclipped to continue the pattern, every tile is
clipped back to the configured columns x rows rectangle (the overall shape never changes, only the
alignment), and the download renderer applies layout + final zoom before capturing the canvas.

Verified with patterned-tile screenshots and download captures
(`CAPTURE_OFFSETS=1 npx playwright test e2e/offsets.screenshots.spec.ts`, output in
`test-results/offset-screenshots/`). Single-axis offsets (the common half-drop case) are fully
correct: exact configured shape, stable scale, no gaps.

- **Offsets/shifts mode**: enabled in the demo, `data-shifts` attribute support, offset sliders hidden unless shifts mode, `calculatedHeight` fixed, shift normalization into `[0, period)` via floor-mod (a wrap translates the strip by exactly one period - invisible for a periodic pattern; the previous signed rounding wrapped at half periods and made tiles visibly jump while dragging), magnitude-based shifts with the vertical stagger direction following the horizontal one (validated in a standalone coverage model: zero uncovered cells for every offset sign combination at moderate values), ring-adjacent margin tiles render unclipped with the neighboring strip phase (fills the crop-boundary wedges), every tile is clipped back to the configured columns x rows rectangle (the overall shape is preserved, overlapping parts are clipped), leftover wedges from large/wrapping offsets are filled by repositioned spare (hidden) tiles scanned in quarter-tile steps (the pattern is periodic, so a tile at any position shows the correct content for it), the shift-formula margin/overlap/inset machinery removed, the download renderer applies layout + `fitBounds` + `forceRedraw` before capturing (previously the readiness was checked against an empty world and the canvas was captured in a mixed-zoom state), debug handle `osdRenderer` exposed on the output viewer element
- **Offsets + rotations** (formerly O1): the offset shift magnitude was computed via `imageToViewportRectangle`, which bakes the tile rotation into the rectangle (OpenSeadragon normalizes rotated rectangles by swapping width/height) - for 90/270 degree rotated tiles the magnitude collapsed to 0 and the tiles stayed behind while their rows/columns shifted ("wrong direction"). `OffsetRect.calculateX/calculateY` now scale the raw image-space magnitude with a rotation-independent tile scale (`OffsetRect.viewportScale`). The crop-clip trim applied the overflow to the clip's unrotated axes - rotated tiles stuck out of the configured area or lost content at the wrong edge (visible as a notch in the download); the trim now maps the overflowing viewport sides to the correct clip sides per tile rotation (90 degrees swaps the axes, 180 flips them)
- **Rotation rewrite** ("rotation is broken in normal mode", "unrotated tiles jump when rotating"): three root causes fixed.
  1. The layout reused the previous layout's state: the crop-clip trim read `getClip()` (the previous layout's already-trimmed clip) and trimmed again, eroding boundary tiles further on every relayout; the rotation block rotated the previous clip again. Every layout now starts each tile group from a defined state (rotation 0, clip = the untouched cut region) - layouts are stateless and idempotent.
  2. The rotation compensation was a margin-based approximation ("ugly hack") that misaligned rotated tiles whenever the cut region had margins inside the image (visible with any real cut). Replaced with exact centering math: OpenSeadragon rotates the content about the tile's world center, so the world center is shifted by the rotated offset between the clip center and the world center - the rotated cut region lands exactly where the unrotated one was, relative to the grid cell. The clip is no longer rewritten (the tile's rotation rotates exactly the cut region); the setWidth/setHeight and clip-mutation hacks are gone.
  3. The crop-clip measured the tile's bounds BEFORE the position was applied (reading the world's arrange() placement) - a regression from the drawn-bounds measurement. The position is now applied before the crop logic measures the drawn (clipped) bounds, which for rotated tiles are the rotated clip region.
     Note: an earlier attempt additionally called `TiledImage.reset()` per tile per layout to guard against "stuck" sub-tiles - reverted: clearing the tile cache forced every tile to re-fetch asynchronously, which made every change flicker and render partially empty content. Cached sub-tiles are clip/position-independent (same source image), so incremental redraws from cache are correct and flicker-free; the staleness was caused by the state accumulation fixed in (1).
     Test coverage added (`e2e/rotation.spec.ts`): rotating must not move unrotated tiles; layouts must be stateless (rotate 90 and back restores the exact original state, positions + clips + rotations); repeated identical relayouts must not erode tiles; rotated tiles must keep their grid cells (full-image cut); rotated tiles must keep their cells with a PARTIAL cut region (the case that exercises the compensation - the previous tests never covered it because the mock's default cut equals the full image, making the compensation a no-op)
- **Wedge filler correctness** ("gaps at the visual edge when a tile is offset out of the configured area"): the filler scan's coverage test only checked whether a quarter cell's top-left corner point lay inside some tile's drawn rect - a tile merely grazing that corner marked the whole cell as covered, leaving the rest of it empty. Rewritten with exact union coverage: every drawn rectangle is subtracted from the scan cell (rectangle difference), and only cells with nothing left over count as covered - cells jointly covered by neighbouring tiles of the same strip stay untouched (no seams introduced), genuine gaps get filled. The fillers themselves are now phase-correct: the scan groups uncovered cells greedily into blobs that never cross a pattern-period boundary in either axis, and each filler tile is positioned at the period-aligned window start with a clip carrying the blob's phase (a tile draws its clip region offset from its world origin, so the origin and the clip phase must be paired). Validated in the standalone coverage model: zero uncovered samples for every offset combination, at most 4 of 36 spare tiles deployed, and zero fillers for the clean single-axis cases. Regression test added (`combined offsets leave no uncovered area when edge tiles disappear`): rasterizes the configured area with 4096 sample points re-derived from the live OpenSeadragon state and asserts every point is covered
- **JSON export/import round-trip**: `toJSONLD` overwrote `body.value` (the structured cuts/offsets/rotations object) with the SVG pattern string, so the exported document lost the offsets entirely and a re-import only restored the lossy SVG approximation. The structured state now rides along the SVG (`body.cuts`, `body.offsets`, `body.rotations` - `body.value` stays the SVG for pattern consumers), and `loadJSONLD` prefers the structured fields over the SVG-derived approximation. Two export bugs fixed en route: `expandPositions(..., all=true)` iterated `Object.keys(CutPosition)` (the names AND the reverse mappings), and `toString` of a name key returns the numeric enum value - the exported objects carried garbage keys like `"0": 0`; the expansion now iterates the four enum values explicitly. Only the active (non-zero) offset/rotation entries are exported: zeros are meaningless and would break the Left/Right and Top/Bottom exclusivity on re-import. Tests: the export contents (cuts/offsets/rotations + the SVG pattern + the selector), the full download → re-drop → download round-trip equality, the offsets/rotations upload, and an invalid JSONLD error
- **Help screen**: a "?" button next to the viewer buttons opens a native `<dialog>` listing all controls (grid size, cut sliders, offset sliders, rotation knobs, rulers, zoom, downloads, drag & drop upload). - **Renderer source-load races** (found via the easter egg, which loads a single-tile-per-item image source): `Renderer._loadTiles` resolved after N global `tile-loaded` events, but tiles are only requested for items inside the viewport and `preserveViewport` keeps the previous viewport after the first open - single-tile sources never reached the threshold while the remaining tiles streamed in after the layout, so the promise hung, `arrange` ran without `preview`/`layout` (raw grid with gaps, no crops) and every cut/offset/rotation notification queued up silently instead of applying (output stuck, "only the tiles change" on reload). Readiness is now tracked per item (added items report fully loaded as soon as they have no tiles left to load, which is immediately true for items outside the viewport), concurrent loads are serialized with a generation counter (a superseded load neither applies its layout nor reports its failure), `open-failed` rejects instead of hanging, and the viewer `close` handler aborts the pending load. En route fixed: the `_notificationQueue` was iterated but never drained, so every load replayed all stale notifications with coordinates of previous (differently sized) sources - it is now spliced on consumption and cleared in `clear()`; replayed notifications apply directly (a trailing full `preview()` after a replay would reset the clip and drop the restored cuts); `CuttingTable.set imageService` now always clears the renderer (the `loaded` gate left the previous source's image-space `clipRect`/`_offsets` behind whenever a load did not complete). Test coverage added (`e2e/easteregg.spec.ts`): real rendering assertions (loaded flag, item count, clip rect, empty status, seamless grid coverage sampled from the live state), toggle-back restores the IIIF image and its transformation, cuts are preserved proportionally across the toggle, and a toggle during a load is queued and applied. `e2e/helpers/app.ts` `loadTestImage` now also waits for the output renderer's first completed layout - the cutting-table-side signals it waited on can fire before the first arrange/preview/layout, which made world-snapshot tests race a raw arrange placement
- **Easter egg**: pressing Escape swaps the loaded pattern for a generated carpet (`src/easterEgg.ts`, wired with a single `installEasterEgg(this)` call in `CuttingTable.setupControls`) - the SVG becomes the image source through the regular `imageService`/`imageServiceUrl` pipeline, so cuts, offsets, rotations, download and JSON export all work on it; pressing Escape again restores the previous source. The active cut is mapped proportionally onto the other source in both directions, a toggle pressed while a load is still in flight is queued behind the running load (a 5s safety timeout keeps a failing load from wedging the control), the listener ignores Escape meant for the help dialog, form controls and other generator instances, and nothing happens when no image is loaded yet
- **Offset slider flicker** ("jumps, flickering at the edges" while dragging offset-x): three root causes fixed.
  1. Wedge fillers landed off-target and overlapped real content: a filler tile draws its clip region offset from its world origin, but the positioning math omitted the cut origin - every filler was shifted by (`clipRect.x`, `clipRect.y`) in scale units, so it overlapped already-covered tiles (popping that reads as changing z-order) while the genuine gap stayed empty. Only invisible when the cut starts at (0, 0). The origin now subtracts the cut origin, so the drawn region lands exactly on the uncovered area with the matching source phase.
  2. The filler covered the coarse scan blob instead of the exact gap: the blob is grown on a quarter-cell grid and can extend over already-covered areas. The blob's exact uncovered remainder is now computed (reusing the coverage subtraction) - empty remainders deploy nothing instead of wasting a spare on an overlap, and the filler is clipped to the remainder's bounding box.
  3. The viewport chased every tick: `preview()` refit to the measured union of drawn tiles, which jumps whenever boundary tiles flip hidden/visible/trimmed or fillers deploy. The viewport now fits the configured columns x rows rectangle (which only changes with the cut, the grid or the source scale), so framing stays put while interacting.
  En route fixed: the coverage scan had no tolerance, so float slivers along tile edges registered as uncovered - placed rects are now expanded by 1e-6 in the subtraction; `Cuts.offsetX`/`offsetY` notified unconditionally (unlike the guarded `rotateX`/`rotateY`), now no-ops when nothing changed. Test coverage added (`e2e/offsets.stability.spec.ts`): scripted offset-x and offset-y drags assert bit-identical viewport zoom/center on every tick, zero pairwise tile overlap, and empty status - the test fails on the old code on both axes.
